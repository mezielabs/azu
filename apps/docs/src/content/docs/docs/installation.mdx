Azu runs inside your AdonisJS app, at `/admin`. You'll add Bouncer, install Azu, and write one rule that says who gets in.

This guide assumes you can run Ace commands and edit TypeScript in an existing AdonisJS app. You should know how your app signs users in. Resource definitions also use Lucid models, Bouncer policies, and VineJS validators.

## Requirements

- AdonisJS 7, Lucid 22, Auth 10, Bouncer 4, and VineJS 4.
- `@adonisjs/inertia` 5 for the server integration.
- React 19, React DOM 19, and `@inertiajs/react` 3 for the panel.
- Vite 8, `@adonisjs/vite` 6, and Edge 6.
- Node.js 24.21 or later.
- PostgreSQL, MySQL, or SQLite.

The panel also needs Vite, Edge, an Inertia config and provider, and a session guard. Configure checks your app's files before it makes changes. If it finds a Vite or Inertia config but can't confirm its provider, it warns you and continues. See [Ace commands](/docs/reference/commands/#configure) for the checks.

Note: the React and Vue starter kits have everything but Bouncer. The Hypermedia kit needs two more steps, and the API kit isn't supported yet. [Starter kits](/docs/starter-kits/) has the details.

## Install

<Steps>

1. If your app doesn't have Bouncer, add it. Azu's access gate is a Bouncer ability, and the AdonisJS starter kits don't include Bouncer.

   ```sh
   node ace add @adonisjs/bouncer
   ```

2. From your app's root directory, install both Azu packages with the `preview` tag. Use `pnpm add` or `yarn add` if you prefer.

   ```sh
   npm i @mezielabs/azu@preview @mezielabs/azu-react@preview
   ```

3. Configure Azu:

   ```sh
   node ace configure @mezielabs/azu
   ```

   A successful configure creates `config/azu.ts` and `inertia/admin/app.tsx`. Resolve any provider warnings before opening the panel.

4. Decide who gets in, as described below. Configuring adds an `accessAdmin` ability to `app/abilities/main.ts` that returns `false`.

</Steps>

## What configure does

Configuring Azu:

- registers its provider and creates `config/azu.ts`.
- mounts the panel at `/admin`.
- adds a separate Vite entry, so your public pages never load admin code.
- adds the `accessAdmin` ability to `app/abilities/main.ts`.

## Let people in

`accessAdmin` decides who can open the panel. The demo store lets in admins and staff:

<DemoCode file="app/abilities/main.ts" region="access-admin" />

On a fresh starter kit, allow your email while you try Azu locally. Add the `User` import and replace the generated `accessAdmin` ability:

```ts title="app/abilities/main.ts"
import type User from '#models/user'

export const accessAdmin = Bouncer.ability((user: User) => {
  return user.email === 'you@example.com'
})
```

:::caution
Before deploying, use a rule tied to a trusted account or role. With public signup, someone else can register an allowlisted email unless your app verifies ownership.
:::

Note: if you added Azu before Bouncer, run `node ace add @adonisjs/bouncer`, then `node ace configure @mezielabs/azu` again to add the ability. Without Bouncer, Azu denies everyone.

## Signing in

Azu uses your app's existing auth guard. Guests are sent to your login page, and signed-in users who fail `accessAdmin` get a 403.

With session middleware, Azu remembers the admin page a guest asked for. Your login can send them back there. [Troubleshooting](/docs/troubleshooting/#login-doesnt-return-to-the-admin) shows the demo's login controller.

## Verify access

If your dev server isn't running, start it:

```sh
npm run dev
```

Check that your login works and the account you allowed can open `/admin`. Before you add resources or a home screen, the panel shows a welcome page. Signed-in accounts outside the access rule should receive a 403.
