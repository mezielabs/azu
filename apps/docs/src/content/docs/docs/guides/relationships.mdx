A product belongs to a category and has many tags. Azu reads those relationships from your Lucid model. You choose where they show.

## belongsTo

A `belongsTo` column shows the related record's title, and Azu preloads it:

A `belongsTo` field is a searchable select that loads options as you type. `searchable()` names the column it searches, or the related resource's `title` without it:

<DemoCode file="app/admin/resources/product_resource.ts" region="fields" mark={["field.belongsTo('category')", "field.manyToMany('tags')"]} title="app/admin/resources/product_resource.ts (fields)" />

It submits its foreign key (`category` → `categoryId`), so your validator checks `categoryId`.

Note: the field is read-only for users who can't list the related resource. It still shows the current record, but offers no options and never writes.

## hasMany

A `hasMany` field shows a table on the detail page. It uses the related resource's columns, except the `belongsTo` back to this record. A category's products table has no Category column.

## manyToMany

A `manyToMany` field, the second one marked above, is a searchable picker that adds and removes related records. It submits the related records' keys under the relation's singular name plus `Ids` (`tags` → `tagIds`). So your validator checks an array:

<DemoCode file="app/validators/product.ts" region="tag-ids" />

Azu syncs the pivot rows with the validator's output, in the same transaction as the save. A failure rolls back both.

- Leave `tagIds` out of a request, and the attached records stay as they are.
- Send an empty list to detach them all.
- This works when the form uploads a file too. Azu sends an empty selection as the string `[]`, and restores the array before validation.

### When the picker is read-only

The picker is read-only for users who can't list the related resource.

It's also read-only on edit when the related resource's `query` scope hides some attached records. The form explains why. The server checks the scope again on submit, and ignores changes to that field. The whole attachment set is kept. Its current keys still reach the validator.

### More than 200 attached

The edit form loads up to 200 attached records. For a record with more, the field is read-only, with a note: "350 tags attached; too many to edit here". It leaves `tagIds` out, so saving never detaches the ones it didn't load.

The server applies the same rule. A `tagIds` sent anyway is ignored, and doesn't reach your validator either.

## Keys

Picker and filter values use Lucid's configured relation key: `localKey` for `belongsTo`, and `relatedKey` for `manyToMany`. Detail links still use the related record's primary key.

## Filters

`filter.belongsTo('category')` filters the list by a related record. See [Filters](/docs/guides/filters/#filter-kinds).

## Validating related IDs

Picker options run through the related resource's `query` hook. That limits what the picker offers, but doesn't validate newly submitted keys.

Your validator decides which related records a user may attach. A plain `exists()` rule only checks whether a record exists. For scoped data, add the same access restrictions to that rule.

For example, another app might assign projects to categories and tags within a workspace. Its update validator could be:

```ts title="app/validators/project_assignments.ts"
import vine from '@vinejs/vine'

export const updateProjectAssignmentsValidator = vine
  .withMetaData<{ workspaceId: number }>()
  .create({
    categoryId: vine.number().exists({
      table: 'categories',
      column: 'id',
      filter: (query, _value, field) => {
        query.where('workspace_id', field.meta.workspaceId)
      },
    }),
    tagIds: vine
      .array(
        vine.number().exists({
          table: 'tags',
          column: 'id',
          filter: (query, _value, field) => {
            query.where('workspace_id', field.meta.workspaceId)
          },
        })
      )
      .optional(),
  })
```

This example assumes numeric IDs and a `workspace_id` column on both related tables. Merge these rules with any other writable fields' rules.

Supply the workspace from trusted server-side state. In an app whose `web` user has a `workspaceId`, the resource's validator options are:

```ts title="app/admin/resources/project_resource.ts (validators option)"
validators: {
  update: updateProjectAssignmentsValidator,
  meta: ({ ctx }) => ({
    workspaceId: ctx.auth.use('web').user!.workspaceId,
  }),
},
```

Import the validator from `#validators/project_assignments`. Match the guard to your app. For create forms, apply the same rules to the create validator too.

Never take the workspace ID from the submitted form. Test a forged request with a related ID outside the workspace: validation must reject it.

The read-only protections described above still apply. They preserve existing attachments; they don't authorise newly selected records.
